# Staging محلی RastiSi روی لپ‌تاپ ویندوز

این پروژهٔ Compose برای بررسی SHA
`5732e12cf21703624ee6acb51aa4c81b6ee54900` است. شاخهٔ ابزار Staging
فقط دستورهای اجرا را دارد. تصویر برنامه از درخت Git همان SHA ساخته می‌شود
و قبل از اجرا SHA از label تصویر بررسی می‌شود. lock آمادهٔ wheel فقط برای
Linux AMD64 و Python 3.12 است. tagهای تصویر زیرساخت patch را به‌روز می‌کنند؛
اگر تکرار بایت‌به‌بایت لازم است digestهای آزمایش مورد تأیید را ثبت و بررسی کنید.

## اول بررسی فقط‌خواندنی

در PowerShell، از پوشهٔ `deploy/local-staging` اجرا کنید:

```powershell
powershell -NoProfile -File .\Check-Laptop.ps1
```

اسکریپت نسخه و معماری Windows، RAM، فضای آزاد، وضعیت virtualization،
نسخهٔ توزیع WSL و وضعیت engine/Compose را می‌خواند. هیچ ابزار یا ویژگی را
فعال یا نصب نمی‌کند. Linux AMD64، توزیع WSL نسخهٔ ۲، Docker Linux engine
محلی، Compose v2 و Git لینوکسی لازم‌اند. ۸ GiB RAM میزبان و ۱۵ GiB فضای
آزاد برای شروع پیشنهاد می‌شود؛ خواب Windows پایش طولانی را وقفه‌دار می‌کند.
اگر Docker Desktop مجوز رایگانِ مناسب کاربرد شما ندارد، پس از تأیید شما
از Docker Engine و Compose plugin در WSL2 استفاده کنید. Docker Desktop
و Docker Engine مستقل داخل WSL را هم‌زمان به یک پروژه متصل نکنید.
خروجی را خصوصی بفرستید. این بررسی در Cloud جای بررسی لپ‌تاپ را نمی‌گیرد.

## پس از تأیید راه‌اندازی محلی

checkout شاخهٔ PR را داخل home توزیع WSL بگیرید تا Git فایل‌های shell را با
LF بخواند. از فولدر ابزار، ابتدا دسترسی engine و سپس مراحل زیر را اجرا کنید:

```bash
cd deploy/local-staging
bash stage.sh check
bash stage.sh prepare
bash stage.sh up --approve-local
bash stage.sh status
bash stage.sh test
bash stage.sh soak
bash stage.sh stop
```

`prepare` اگر SHA را محلی ندارد از origin همان checkout دریافت می‌کند و
برای base imageها و wheelهای hash-verified به رجیستری و PyPI دسترسی دارد.
اگر رجیستری بستهٔ Python از داخل Docker قابل دسترسی نیست،
`bash stage.sh prepare /absolute/path/to/verified/wheelhouse` با wheelhouse
تأییدشده پشتیبانی می‌شود. TLS و بررسی hash برقرار می‌مانند. runtime از
شبکهٔ build جداست. `up` فقط تصاویر آمادهٔ محلی را می‌گیرد و به گزینهٔ
تأیید نیاز دارد. آدرس لپ‌تاپ `http://127.0.0.1:18080/` است.
`stop` کانتینرها را برمی‌دارد و volumeهای مصنوعی را برای اجرای بعدی
حفظ می‌کند. در حین test یا soak مرحلهٔ stop را اجرا نکنید.

## مرز ایزوله و آزمون‌ها

Compose تنها یک شبکهٔ داخلی دارد. فقط Nginx روی loopback پورت منتشر
می‌کند. appها، PostgreSQL و Redis پورت میزبان ندارند. تنظیمات هر سرویس در
Compose مشخص‌اند، فایل env واقعی وارد نمی‌شود، اتصال Docker از راه دور رد
می‌شود، Docker socket به کانتینر داده نمی‌شود و volumeها محلی و مختص این
پروژه‌اند. برنامه از پایگاه خالی، migrationهای همان SHA و یک فایل Media
مصنوعی شروع می‌کند. پرداخت در حالت شبیه‌سازی است. OTP فقط console و ایمیل
dummy است. هیچ اعتبارنامهٔ ارائه‌دهنده‌ای وارد نکنید. Nginx فقط volumeهای
public و static را می‌بیند و به volume خصوصی دسترسی ندارد.

`test` صفحات اصلی/ورود/ثبت‌نام و فایل عمومی را می‌سنجد، Gunicorn اول را
کامل متوقف می‌کند و چند دور پاسخ را از Nginx می‌گیرد، سپس آن را بازمی‌گرداند
و با توقف یک worker آزمایشی، timeout و جایگزینی PID را کنترل می‌کند.
شناسهٔ درخواست و زمان ثبت‌شده در دو لاگ تطبیق داده می‌شوند. مسیر retry فقط
برای GET/HEAD است. این آزمایش تضمین ظرفیت واقعی یا حذف همهٔ درخواست‌های
ناموفق هنگام خرابی نیست. `soak` هر ۶۰ ثانیه طی ۶۵ دقیقه از داخل شبکه سه
صفحهٔ عمومی را می‌سنجد و گزارش `soak.jsonl` می‌نویسد. دو خطای متوالی در
همان صفحه یا نمونهٔ نهایی ناموفق، کد خروج غیرصفر می‌دهد.

این Staging محلی HTTP است و پایش آن فقط هنگام روشن‌بودن لپ‌تاپ معتبر است.
آزمون مستقل TLS/WAN، دریافت هشدار مالک، DNS و خرابی کل میزبان را پوشش
نمی‌دهد. اگر برنامهٔ آینده به انتشار عمومی نیاز داشت، پیش از ایجاد تونل
یا تغییر DNS باید طرح جدا تأیید شود: TLS معتبر، احراز هویت، محدودیت
مسیرهای خواندنی، جلوگیری از ورود عمومی به admin و عدم انتشار DB/Redis،
timeout/rate limit، بازهٔ زمانی محدود، و خاموش‌کردن و حذف مسیر پس از آزمون.
هیچ تونل یا DNS در این پروژه فعال نمی‌شود.

Docker برای مسیریابی، خرابی فرایند، ثبت لاگ، دادهٔ مصنوعی و soak کافی است.
Docker مسیر واقعی systemd، cgroup، reboot، sandbox واحدها و مجوز RuntimeDirectory
روی میزبان نصب را شبیه‌سازی کامل نمی‌کند. برای آن بخش یک VM محلی Linux با
systemd واقعی، شبکهٔ جدا و دادهٔ مصنوعی کافی است. VM ساعتی فقط وقتی مطرح
است که اعتبارسنجی مستقل اینترنت/شبکهٔ VPS یا خصیصهٔ خاص میزبان لازم باشد و
VM محلی قابل استفاده نباشد. هزینه و انتشار عمومی هر دو نیاز به تأیید جداگانه دارند.
