## بررسی صرفاً خواندنی برای مالک یا اپراتور

1. بازهٔ ۱۱:۰۲ تا ۱۲:۱۰ را با timestamp دقیق از
   `journalctl -u rastisi-rc-20261111.service --since '2026-11-19 07:32:00 UTC' --until '2026-11-19 08:40:00 UTC' -o short-iso-precise`
   استخراج کنید. PIDها و زمان timeout و SIGKILL را با لاگ خطا و access
   Nginx تطبیق دهید. اگر فیلدهای request_time، upstream_response_time،
   upstream_addr و upstream_status قبلاً ثبت می‌شدند، نمونه‌ها را بر حسب
   route نرمال‌شده و status تجمیع کنید. URL کامل، query، IP مشتری،
   Cookie، Headerهای احراز هویت و محتوای درخواست را منتشر نکنید.
2. خروجی محدود `systemctl show rastisi-rc-20261111.service -p MainPID -p NRestarts -p User -p WorkingDirectory -p DropInPaths -p MemoryCurrent -p TasksCurrent`
   را بررسی کنید. `systemctl cat`، ExecStart، فایل تنظیم Gunicorn و فقط
   کلیدهای مرتبط مانند HOME، XDG_RUNTIME_DIR و تنظیم سوکت را خصوصی مرور کنید.
   نسخهٔ دقیق Gunicorn را از metadata بستهٔ نصب‌شده در venv و lock همان
   artifact بخوانید. فرمان، فایل محیط و خروجی کامل inspect را به GitHub نبرید.
3. با `ss -lntp` و `ss -lxnp` و مرور خصوصی server/locationهای
   `nginx -T` تعیین کنید هر host به 18082 یا `/run/rasti.sock` می‌رود.
   PID قدیمی را صرفاً ثبت کنید. دسترسی مسیر و symlink را با `namei -l`
   بررسی کنید.
4. `journalctl -k` همان بازه را برای OOM و فشار حافظه بررسی کنید.
   تاریخچهٔ CPU، I/O، inode و دیسک، محدودیت/مصرف FD و cgroup را اگر ثبت
   شده جمع کنید. در PostgreSQL فقط وضعیت تجمیعی wait eventها از
   `pg_stat_activity`، lockها و کندی‌های از قبل ثبت‌شده را بررسی کنید.
   برای Redis فقط metrics موجود latency، blocked clients، evictions و
   خطای اتصال را بخوانید. snapshot جاری برای بازسازی قطعی گذشته کافی نیست.
5. با تأیید اپراتور، HTTPS بیرونی و TLS محلی با DNS pin را برای همان
   مسیرها اندازه بگیرید. Gunicorn مستقیم را با Host صحیح و scheme HTTPS
   آزمایش کنید و رفتار trusted proxy را در نظر بگیرید. status و latency را
   ثبت کنید. اختلال هم‌زمان مستقیم و Nginx نشانه‌ای برای بررسی upstream یا
   dependency است. سلامت محلی با خطای صرفاً بیرونی مسیر DNS، TLS یا شبکه را
   در اولویت بررسی قرار می‌دهد.

## سوکت کنترل و تشخیص توقف بعدی

Gunicorn 27.0.1 در wheelhouse آزمون، در حالت پیش‌فرض از
`$XDG_RUNTIME_DIR/gunicorn.ctl` استفاده می‌کند و در غیاب آن به HOME
بازمی‌گردد. drop-in نمونهٔ `deploy/release/examples/gunicorn-runtime.conf`
یک دایرکتوری خصوصی 0700 با مالک حساب سرویس در `/run` تعریف می‌کند.
این drop-in مستقل از بازنویسی ExecStart و انتشار برنامه است. پیش از نصب
تأیید کنید که تنظیم صریح control_socket یا override دیگری مسیر پیش‌فرض
را عوض نمی‌کند و gunicornc قبلی به مسیر دیگری وابسته نیست. نسخهٔ نصب‌شده
را هم تطبیق دهید. برای پنجرهٔ مجاز کنترل کنید systemd پس از راه‌اندازی
سرویس دایرکتوری را با مالک درست ساخته و سوکت همان‌جا فعال است. برای
بازگشت drop-in مستقل را بردارید و تغییر سرویس را در پنجرهٔ تأییدشده اعمال کنید.

در رخداد بعدی، هشدار داخلی روی WORKER TIMEOUT، تغییر PID worker،
Nginx upstream 5xx/P95، فشار منابع و کمبود دیسک/inode، تراکم connection و
wait دیتابیس و خطای Redis تنظیم کنید. از ابزار گردآوری فعلی یا مانیتور
مستقل میزبان استفاده کنید. برای جزئیات زمان درخواست، اگر قبلاً موجود نیست
در پنجرهٔ مجاز یک access log خصوصی با زمان upstream و route پاک‌سازی‌شده
فعال کنید. زمان timeout یا concurrency فقط پس از شناسایی مسیر کند و
برآورد ظرفیت PostgreSQL و Redis تغییر کند.

## مشاهدهٔ بیرونی، هشدار و تصمیم انتشار

- URL پایهٔ canonical را در `PRODUCTION_URL` و یک URL کامل HTTPS
  عمومی و بی‌خطر از tenant نماینده را در `RASTISI_TENANT_URL` تنظیم کنید
  (هم در scope مورد نیاز job انتشار و هم برای workflow مستقل). مسیر نمونه
  باید بدون redirect پاسخ 200 HTML بدهد.
- پس از تأیید مالک، برای workflow مستقل `RASTISI_AVAILABILITY_ENABLED=true` را
  در متغیرهای مخزن تنظیم کنید. workflow مستقل هر ۵ دقیقه درخواست home/login/register/tenant می‌فرستد و
  پس از دو failure پی‌درپی روی همان مسیر با فاصلهٔ ۶۰ ثانیه هشدار می‌دهد.
  GitHub schedule ممکن است تأخیر داشته باشد. برای SLA یک سرویس uptime مستقل
  در دو شبکه به همراه هشدارِ فقدان probe تنظیم کنید.
- `RASTISI_AVAILABILITY_WEBHOOK` اختیاری و فقط HTTPS است. endpoint باید
  JSON شامل message و routes را بپذیرد و به مالک ارسال کند. ابتدا در staging
  با مقصد آزمایشی دریافت اعلان را تأیید کنید. بدون webhook، annotation و
  شکست job ثبت می‌شود و دریافت قطعی هشدار توسط مالک باید جداگانه آزموده شود.
- درخواست‌ها GET بدون credentials و بدون ارسال فرم‌اند و status و مدت
  را ذخیره می‌کنند. login/register ممکن است session معمول مرورگر بسازند.
  ALTCHA صراحتاً session، rate limit و challenge در cache ایجاد می‌کند.
  مسیر ALTCHA را با حساب یا مرورگر بدون اطلاعات مشتری صرفاً در rehearsal
  مجاز و با بودجهٔ نرخ کنترل کنید و پاسخ JSON را بدون ذخیرهٔ challenge
  اعتبارسنجی کنید. این URL در پایش دائمی قرار نگرفته است.
- پس از Activate واقعی، runner ۶۵ دقیقه پایش می‌کند، بیش از فاصلهٔ حدود
  ۵۳ دقیقهٔ رخداد. شکست‌های پیاپی یا شکست نمونهٔ انتهایی، job را ناموفق
  می‌کنند. گزارش JSONL در artifact می‌ماند. پس از soak شناسه و SHA سرویس‌دهنده
  دوباره بررسی می‌شود. هم‌زمان نمودارهای داخلی و قبل/بعد worker را بررسی کنید.
- شکست soak هشدار عملیاتی است و برنامه ممکن است همچنان فعال باشد. ابتدا
  SHA سرویس‌دهنده، وضعیت اجرا و incident را کنترل و بیرون/داخل را مقایسه کنید.
  بازگشت فقط با مجوز مالک، نسخهٔ قبلی سالم، schema سازگار و بکاپ قابل‌بازیابی
  انجام شود. gate بیرونی فرمان بازگشت صادر نمی‌کند.

### خروجی پاک‌سازی‌شده برای پیشبرد تشخیص

مالک می‌تواند روی میزبان، با سطح دسترسی خواندن journal و پردازهٔ سرویس،
فرمان زیر را اجرا و JSON را **خصوصی** منتقل کند.

```sh
python3 -B deploy/release/availability_diagnostics.py \
  --since 2026-11-19T11:02:00+03:30 --until 2026-11-19T12:10:00+03:30
```

ابزار فایل خروجی، اتصال HTTP، اتصال دیتابیس، سیگنال یا فرمان تغییر وضعیت
ندارد. فقط زمان، نوع رخداد و PID عددی مجاز و snapshot محدود را چاپ
می‌کند. بررسی argv و env فقط چند نشانهٔ بولی را برمی‌گرداند. نسخه از
metadata دایرکتوری venv فعلی گزارش می‌شود. این داده جای بررسی دقیق config
Gunicorn را نمی‌گیرد. وجود دو listener مسیر واقعی Nginx را اثبات نمی‌کند.
اگر journal Nginx خالی است، اپراتور باید از access/error log موجود فقط
زمان، وضعیت و دستهٔ upstream را بدون URL، IP، Cookie و شناسهٔ مشتری جمع‌بندی
کند. اگر دادهٔ تاریخی موجود نیست، شکاف تشخیص را ثبت کنید.

برای مانیتور مستقل، دو ناحیهٔ بیرونی با فاصلهٔ یک‌دقیقه‌ای و آستانهٔ دو خطا
تعریف کنید. مسیرهای canonical بالا، timeout هشت‌ثانیه‌ای و TLS validation
را تنظیم کنید. یک endpoint آزمایشی که عمداً دو بار 503 می‌دهد برای
تأیید تحویل webhook به **خود مالک** استفاده شود. تأیید دریافت همراه زمان
ثبت شود و هشدار فقدان نمونه در مانیتور مستقل نیز فعال شود.

### تطبیق لاگ فایل Nginx با timeout

گزارش خواندنی مالک، Gunicorn 27.0.1، timeout پردازهٔ 2575151،
جایگزینی با PID 2583767، خطای مجوز سوکت کنترل و وجود سوکت قدیمی را
تأیید کرد. در journal کرنل با الگوهای بررسی‌شده OOM دیده نشد.
journal خالی Nginx برای نتیجه‌گیری دربارهٔ upstream کافی نیست.

فایل‌های واقعی access و error مربوط به همین virtual host و همان بازه
را از تنظیمات موجود شناسایی کنید. اگر لاگ فایل اختصاصی یا rotated دارید
گزینه‌ها را برای هر فایل تکرار کنید. نمونه:

```sh
python3 -B availability_diagnostics.py \
  --since 2026-11-19T11:02:00+03:30 --until 2026-11-19T12:10:00+03:30 \
  --nginx-host rastisi.ir \
  --nginx-access /var/log/nginx/access.log \
  --nginx-access /var/log/nginx/access.log.2.gz \
  --nginx-error /var/log/nginx/error.log \
  --nginx-error /var/log/nginx/error.log.1
```

نام‌ها نمونه‌اند و باید با فایل‌های موجود تطبیق داده شوند. بدون گزینه،
حداکثر هشت فایل معمول از هر نوع در مسیر پیش‌فرض خوانده می‌شود. خطاهای
Nginx بدون offset با منطقهٔ زمانی `--since` تفسیر می‌شوند. خروجی زمان
اول و آخرِ قابل خواندن، شمار رکوردهای نامعتبر، قطع‌شدن به‌دلیل سقف و
مجموع و بیشینهٔ زمان upstream را گزارش می‌کند. برای زمان‌های میانگین،
`total_ms` را بر `timed_attempt` همان upstream تقسیم کنید.
فرمت combined قدیمی فقط status دارد. upstream واقعی از فیلد ساختاریافته
یا متن خطای upstream به سه دستهٔ پورت release، سوکت legacy و سایر
تقلیل می‌یابد. هیچ IP دیگر، header، query، URL، request ID، مسیر فایل
ورودی یا متن لاگ در JSON چاپ نمی‌شود. شمارهٔ فایل با ترتیب ورودی متناظر است.
برای فایل access مشترک بدون host، شمارش مربوط به کل فایل است.

`within_120s_of_worker_timeout` شمارش دو دقیقه قبل و بعد از هر timeout
را گزارش می‌کند. اگر journal رخداد تاریخی را نداشته باشد، زمان گزارش‌شدهٔ
۱۱:۵۵:۵۶ تهران مبنای مشخص است. نزدیکی زمانی، انتساب یک درخواست به PID یا
اثبات علت توقف نیست. `nginx_config_candidates` فقط فایل فعلی و includeها
را می‌خواند و مقصدهای مستقیم، گروه upstream و مقادیر پویا را برای
server_name دقیق و کل تنظیمات جدا می‌شمارد. این بررسی config فعال در
حافظه، انتخاب location پویا یا config تاریخی را اثبات نمی‌کند. مشاهدهٔ
upstream در لاگ، شاهد مسیریابی واقعی همان رکورد است. از اجرای `nginx -T`
در ابزار صرفاً خواندنی خودداری شده است.

### نتیجهٔ نهایی بررسی تاریخی

**واقعیت‌های تأییدشده.** Gunicorn 27.0.1 در زمان بررسی فعال بود. Worker
با PID 2575151 در ۱۱:۵۵:۵۶ تهران timeout شد و worker جایگزین بالا آمد.
در پنجرهٔ ۱۲۰ ثانیه‌ای یک پاسخ Nginx با وضعیت 499 ثبت شد. در لاگ‌های
بررسی‌شده 502 یا 504 دیده نشد. پیکربندی فعلی `rastisi.ir` به پورت
`127.0.0.1:18082` اشاره می‌کند. سوکت قدیمی همچنان فعال است. لاگ تاریخی
زمان یا مقصد upstream را ثبت نکرده است.

**حد استنتاج.** 499 یعنی اتصال سمت مشتری پیش از تکمیل پاسخ بسته شد.
هم‌زمانی آن با timeout درخواست یا PID متناظر را مشخص نمی‌کند. شواهد
مسیریابی اشتباه نداریم. تنظیم فعلی مسیر تاریخی را اثبات نمی‌کند. علت
توقف worker و نقش احتمالی کندی برنامه، انتظار PostgreSQL، Redis یا
فشار I/O باز هستند. خطای دسترسی سوکت کنترل جداگانه تأیید شده است.

### ثبت خصوصی و ارتباط با هشدار

نمونهٔ `deploy/release/examples/nginx-availability-http.conf` را ابتدا
در staging آزمایش و با حفظ access logها و headerهای موجود به
server/location مربوط اضافه کنید. Nginx شناسهٔ ورودی مشتری را بازنویسی
می‌کند و فقط شناسهٔ ساخته‌شده به Gunicorn می‌رسد. Gunicorn باید روی
loopback باقی بماند. نمونهٔ `gunicorn-availability.py` را با config
مؤثر و hookهای موجود ترکیب کنید. شروع و پایان درخواست معتبر شامل PID،
زمان، شناسهٔ تولیدشده و مدت اجرای کامل است. worker_abort در صورت اجرای
hook ثبت می‌شود. SIGKILL یا توقف کامل می‌تواند مانع اجرای hook شود؛
journal master همچنان منبع WORKER TIMEOUT است. یک PID می‌تواند چند
درخواست gthread هم‌زمان داشته باشد. رخداد بدون پایان تنها فهرست
درخواست‌های احتمالی را محدود می‌کند.

در لاگ جدید روش درخواست، URL، query، IP مشتری، Cookie، Authorization
و بدنه نوشته نمی‌شوند. تنظیمات موجود از جمله error log ممکن است همچنان
اطلاعات درخواست داشته باشند؛ خروجی خام را منتشر نکنید. فایل اختصاصی Nginx
و journal باید فقط برای اپراتور مجاز، با گردش و سقف نگه‌داری در دسترس باشند.
هم‌بستگی شناسه‌ها به‌صورت محلی انجام شود. نمونهٔ استریمی، درخواست ممتد،
مسیرهای خطا و محدودیت حجم/نرخ را قبل از Production بررسی کنید.

هشدار بیرونی اکنون زمان UTC، status و latency دو مشاهدهٔ ناموفق هر مسیر
را می‌فرستد. artifact پاک‌سازی‌شدهٔ `availability.jsonl` را می‌توان با
`--external-observations availability.jsonl` به ابزار خواندنی داد.
گزارش برای هر WORKER TIMEOUT، نمونه‌های موفق و ناموفق ۱۲۰ ثانیه قبل و
بعد را می‌شمارد. در عملیات، هشدار بیرونی همراه timeout نزدیک را به
عنوان رخداد دسترس‌پذیری نیازمند بررسی فوری triage کنید. timeout بدون
هشدار بیرونی یک رخداد داخلی است و هشدار بیرونی بدون timeout باید
از دید شبکه، Nginx و وابستگی‌ها بررسی شود. فاصلهٔ زمانی شاهد هم‌بستگی
است. ساعت runner و میزبان باید همگام باشد.

**شرط انتشار.** CI نهایی، تطبیق config مؤثر Nginx/Gunicorn و مالکیت
runtime، محدودیت دسترسی و گردش فایل، صحت مسیرهای public/tenant در
staging، تمرین مستقل مانیتور بیرونی، مشاهدهٔ کامل پس از انتشار و
تأیید دریافت هشدار توسط خود مالک لازم‌اند. نسخهٔ قبلی تنظیمات و
